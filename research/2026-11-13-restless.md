## Takeaway

Our interpretation: the useful reference is the path from observing an API problem to helping an agent recover and giving the provider something concrete to fix. Compare that promise with Two Hands' evidence and provider-improvement story.

## Source observations

Public pages reviewed on November 13, 2026. These are vendor descriptions, not results of an integration test, customer interview, or independent performance review. No SDK was installed and no account was created.

- Restless is built by ReadMe. Its [about page](https://www.restless.ai/about) frames APIs as a way people access products through agents, extending ReadMe's API documentation work.
- The [homepage](https://www.restless.ai/) presents API logs, support answers, agent feedback, and existing documentation as context for improving API use. It lists MCP access, recovery guidance, and documentation updates among its features.
- [Agent recovery](https://www.restless.ai/agent-recovery) describes putting relevant recovery guidance into failed responses, tracking recovery links, grouping repeated failures, and letting operators edit guidance in a dashboard.
- [Solicit feedback](https://www.restless.ai/solicit-feedback) describes an MCP `send_feedback` tool for agents to report missing capabilities or confusing behavior, with an inbox and a path to create Linear issues.

## Relevance to Two Hands

The following are hypotheses based on those pages and our [current product direction](../docs/PRODUCT_DIRECTION.md):

1. **Overlap worth investigating:** provider-facing agent experience and improvement. Restless could compete for the same buyer attention even if its integration model differs.
2. **Positioning to test:** Restless emphasizes improving a provider's API experience. Two Hands could emphasize the observed task context across tools: what was offered, selected, executed, cited, and reviewed. The pages inspected do not establish whether Restless also captures comparable cross-provider evidence; verify before claiming differentiation.
3. **Product lesson:** a provider may find a reproducible failure plus a suggested fix more useful than an aggregate chart alone. Test whether an evidence-backed issue, a provider change, and a bounded follow-up evaluation creates value.
4. **Measurement boundary:** recovering a failed request and fulfilling the user's task are separate outcomes. Keep execution events, agent feedback, and answer reviews distinct. Agent-reported feedback should not become a verified fact or a measured quality score by itself.

## Questions for next time

- Ask a provider: “What would this tell you beyond your API logs, docs analytics, and support inbox? Show us the last issue that information would have helped fix.”
- Compare one real provider problem through both approaches: what could recovery guidance solve, and what requires task or cross-tool evidence?
- If pursuing a hands-on comparison, first check current docs, supported integrations, access requirements, and pricing. This capture does not establish those details or willingness to pay.
